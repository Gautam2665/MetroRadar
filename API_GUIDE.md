# TransitOS — REST API Reference

This document describes the HTTP API exposed by the TransitOS backend. The API is consumed by the web client, external developers, and analytical tools. All endpoints return JSON. GeoJSON endpoints return standard RFC 7946 FeatureCollection objects wrapped in a versioned envelope.

**Base URL (production):** `https://transitos-33xk.onrender.com`  
**Base URL (local dev):** `http://localhost:3001`

## 1. Response Conventions

### GeoJSON Envelope

All GeoJSON responses are wrapped in a versioned metadata envelope:

```json
{
  "version": "1.0.0",
  "generatedAt": "2026-10-01T09:40:00.000Z",
  "systemId": "MMRDA",
  "type": "FeatureCollection",
  "features": []
}
```

### Realtime Source Labels

All endpoints returning realtime or estimated data include provenance metadata:

```json
{
  "source": "official" | "enhanced" | "estimated",
  "confidence": 0.0–1.0
}
```

| `source` | Meaning |
|:---|:---|
| `official` | Derived from a validated operator GTFS-Realtime feed |
| `enhanced` | Official feed with TransitOS validation and filtering applied |
| `estimated` | Generated by the State Estimation Engine from scheduled data and historical observations |

### HTTP Status Codes

| Code | Meaning |
|:---|:---|
| 200 | Success |
| 400 | Malformed request parameters |
| 404 | Entity not found, or no path exists between given stations |
| 500 | Internal server error |

## 2. Map & GIS Layers

### `GET /map/layers`

Returns the dynamic layer configuration registry. The client uses this to discover available GIS overlays, their endpoint URLs, default visibility, and rendering style. Adding a new analytical layer (e.g., a corridor heatmap or catchment circle overlay) requires only registering it in `geojson.service.ts`; the client renders it automatically.

**Cache:** None (static configuration)

**Response:**
```json
{
  "version": "1.0.0",
  "layers": [
    {
      "id": "lines",
      "name": "Metro Lines",
      "endpoint": "/map/lines",
      "defaultVisible": true,
      "style": { "type": "line", "color": "operator", "width": 4 }
    },
    {
      "id": "stations",
      "name": "Passenger Stations",
      "endpoint": "/map/stations",
      "defaultVisible": true,
      "style": { "type": "circle", "color": "#06b6d4", "radius": 6 }
    }
  ]
}
```

---

### `GET /map/systems`

Returns geographic centre-points and metadata for all registered transit systems.

**Cache Key:** `geojson:systems` (TTL 1 h)

---

### `GET /map/lines?system=<code>`

Returns reconstructed route geometries as GeoJSON `LineString` or `MultiLineString` features, colored by the operator's official line color. Geometry is reconstructed on-the-fly in PostGIS from sequential stop coordinates.

**Cache Key:** `geojson:lines:<system>` (TTL 1 h)

**Query Parameters:**

| Parameter | Type | Description |
|:---|:---|:---|
| `system` | string | Transit system code (e.g., `MMRDA`, `DMRC`). Omit for all systems. |

---

### `GET /map/stations?system=<code>`

Returns all active passenger stations as GeoJSON `Point` features. Each feature's properties include the list of lines served at that station.

**Cache Key:** `geojson:stations:<system>` (TTL 1 h)

---

### `GET /map/stations/:id`

Returns a single station as a GeoJSON `Point` feature.

**Cache Key:** `geojson:station:<uuid>` (TTL 1 h)

## 3. Spatial Search

### `GET /map/search?q=<query>&type=<filters>`

Full-text search against station names, codes, line names, system names, cities, and registered locality names. Results are ranked by relevance; stations and localities rank above physical gates unless the query explicitly includes gate-specific terms ("gate", "exit", "fob").

**Cache Key:** `search:<query>:<type>` (TTL 1 h)

**Query Parameters:**

| Parameter | Type | Description |
|:---|:---|:---|
| `q` | string | Search string (required) |
| `type` | string | Comma-separated entity filter: `station`, `line`, `system`, `locality` |

**Response:** GeoJSON FeatureCollection of matching entities with relevance scores.

---

### `GET /map/nearby?lat=<lat>&lon=<lon>&radius=<metres>&types=<types>`

PostGIS geodesic radius query returning stations or entrances within `radius` metres of the given coordinate, ordered by ascending distance.

**Cache Key:** `nearby:<lat>:<lon>:<radius>:<types>` (TTL 1 h)

**Query Parameters:**

| Parameter | Type | Default | Description |
|:---|:---|:---|:---|
| `lat` | float | — | Latitude (required) |
| `lon` | float | — | Longitude (required) |
| `radius` | integer | 1000 | Search radius in metres |
| `types` | string | `station` | Comma-separated: `station`, `entrance` |

**Implementation note:** Distance is computed using `ST_DistanceSphere` on PostGIS `geometry(Point, 4326)` columns backed by a GIST spatial index.

## 5. Journey Planning & Routing

### `GET /journeys?from=<stationId>&to=<stationId>`

Computes multi-leg transit paths between two stations. The engine generates up to K=5 candidate routes using Yen's K-Shortest Loopless Paths algorithm over the in-memory transit graph, scores each candidate using generalized cost, applies Pareto dominance filtering, and returns the surviving set ranked by score.

**Cache:** None — computed on-demand from in-memory graph.

**Query Parameters:**

| Parameter | Type | Description |
|:---|:---|:---|
| `from` | UUID | Origin station ID (required) |
| `to` | UUID | Destination station ID (required) |
| `systemId` | UUID | Restrict routing to a specific transit system (optional) |

**Response:**
```json
{
  "candidates": [
    {
      "rank": 1,
      "score": 2460.0,
      "attributes": {
        "fastest": true,
        "fewestTransfers": false,
        "direct": false,
        "leastWalking": false,
        "accessibilityFriendly": true
      },
      "from": { "id": "uuid", "name": "Sarojini Nagar", "code": "YL-22" },
      "to":   { "id": "uuid", "name": "IGI Airport T3", "code": "OL-07" },
      "totalDurationSeconds": 2820,
      "totalStops": 14,
      "transferCount": 2,
      "walkingDistanceMeters": 380,
      "legs": [
        {
          "type": "TRANSIT",
          "line": { "name": "Yellow Line", "color": "#facc15" },
          "from": { "name": "Sarojini Nagar" },
          "to":   { "name": "Durgabai Deshmukh South Campus" },
          "stops": 3,
          "durationSeconds": 360,
          "towards": "Samaypur Badli"
        },
        {
          "type": "WALK",
          "from": { "name": "Durgabai Deshmukh South Campus" },
          "to":   { "name": "Dhaula Kuan" },
          "durationSeconds": 300,
          "distanceMeters": 380
        },
        {
          "type": "TRANSIT",
          "line": { "name": "Airport Express", "color": "#f97316" },
          "from": { "name": "Dhaula Kuan" },
          "to":   { "name": "IGI Airport T3" },
          "stops": 2,
          "durationSeconds": 720,
          "towards": "IGI Airport T3"
        }
      ],
      "geojson": { "type": "FeatureCollection", "features": [] }
    }
  ]
}
```

### Scoring Model

The generalized cost score used for ranking:

$$\text{RankScore} = w_t \cdot T_{\text{duration}} + P_{\text{transfer}} \cdot N_{\text{transfers}} + w_w \cdot T_{\text{walking}} + C_{\text{friction}}$$

| Parameter | Default |
|:---|:---|
| $w_t$ (travel time weight) | 1.0 |
| $w_w$ (walking weight) | 0.8 |
| $P_{\text{transfer}}$ (transfer penalty, seconds) | 120 |
| $C_{\text{friction}}$ (interchange friction) | 0–600+ s per node |

### Walk Transfer Edges

Walk edges are inserted automatically between stations whose PostGIS geometries are within the interchange radius (≤ 1000 m on different lines). The edge weight is computed as geodesic distance ÷ 1.2 m/s.

### Error Responses

- `404 Not Found` — No path exists between the given origin and destination.
- `400 Bad Request` — Missing or malformed `from` / `to` parameters.

## 6. Realtime Vehicle Telemetry

### `GET /realtime/vehicles?system=<code>`

Returns current vehicle positions decoded from the operator's GTFS-Realtime Protocol Buffer feed (Level 1/2), or estimated positions from the State Estimation Engine (Level 3). Results are served from Redis with a 30-second TTL. During feed outages, stale cached data is served with `isStale: true`.

**Cache Key:** `realtime:vehicles:<system>` (TTL 30 s)

**Response:**
```json
{
  "system": "DMRC",
  "source": "enhanced",
  "confidence": 0.91,
  "timestamp": "2026-10-01T12:00:00.000Z",
  "vehicleCount": 312,
  "isStale": false,
  "vehicles": [
    {
      "id": "DL-METRO-401",
      "label": "Train 401",
      "lineCode": "YELLOW",
      "latitude": 28.6139,
      "longitude": 77.2090,
      "bearing": 180,
      "speed": 12.5,
      "currentStatus": "IN_TRANSIT_TO",
      "nextStopId": "YL-12"
    }
  ]
}
```

## 7. GTFS Ingestion

### `POST /ingestion/gtfs?systemId=<uuid>&dryRun=<boolean>`

Ingests a GTFS Static zip archive into the Canonical Transit Model (CTM v1.0). The pipeline runs in a transaction-safe session with validation at each stage. In `dryRun` mode, the pipeline validates and reports counts without committing to the database.

**Content-Type:** `multipart/form-data`  
**Form field:** `file` (zip archive)

**Ingestion pipeline stages:**

1. Archive extraction and checksum verification
2. GTFS spec validation (required files, field types, referential integrity)
3. Agency parsing and normalization
4. Route / line parsing with color resolution
5. Stop / station parsing with coordinate validation
6. Trip and calendar parsing
7. Stop-times parsing and travel-time derivation
8. Shapes parsing (optional)
9. Frequencies parsing (optional, for headway-based feeds)
10. Database transaction commit with session tracking

**Response:**
```json
{
  "sessionId": "uuid",
  "status": "SUCCESS",
  "dryRun": false,
  "durationMs": 4200,
  "counts": {
    "agencies":  { "processed": 1,   "inserted": 1,   "updated": 0, "skipped": 0 },
    "stations":  { "processed": 288, "inserted": 288, "updated": 0, "skipped": 0 },
    "lines":     { "processed": 12,  "inserted": 12,  "updated": 0, "skipped": 0 },
    "trips":     { "processed": 842, "inserted": 842, "updated": 0, "skipped": 0 },
    "stopTimes": { "processed": 18400, "inserted": 18400, "updated": 0, "skipped": 0 }
  },
  "warnings": [],
  "errors": []
}
```

## 8. Cache Invalidation Policy

On successful GTFS import, all cached keys matching the following patterns are purged:

- `geojson:*` — all GIS layer caches
- `digitaltwin:*` — all station digital twin caches
- `search:*` — all search result caches
- `nearby:*` — all spatial proximity caches

The routing graph (`transit:graph:*`) is rebuilt on the next routing request.

Realtime vehicle caches (`realtime:vehicles:*`) expire naturally at 30-second TTL and are never actively invalidated by data imports.

## 9. Routing Parameter Sensitivity

The routing engine is designed so that changing any input parameter produces a deterministic, traceable change in outputs. This section documents how parameter changes affect route candidates — answering the question: *what changes when we alter a corridor, station location, or operating assumption?*

| Input Change | Mechanism | Observable Output Change |
|:---|:---|:---|
| Increase transfer penalty (`transferPenalty`) | Scores of multi-transfer paths increase | Fewer-transfer paths rank higher; long direct routes become competitive |
| Increase walking weight (`walkingWeight`) | Walking leg cost increases per metre | Routes with longer feeder walks drop in rank |
| Remove a station from CTM | Station node removed from graph | All paths through that station eliminated; Yen's algorithm finds next-best paths |
| Change `travelTimeFromPrevious` for a section | Edge weight updated in graph | All paths using that section get new duration; may change Pareto ranking |
| Add a new walk edge (interchange connection) | New `WALK` edge inserted in graph | Previously separate lines become reachable without vehicle transfer |
| Move station coordinates | PostGIS `geom` updated | Catchment radius changes; different localities snap to different stations |
| Add a new line / station | New nodes and edges added to graph | New paths emerge; existing paths may gain transfer options |
| Change interchange friction (`C_friction`) | Friction cost in generalized cost changes | Paths through high-friction nodes drop in score relative to alternatives |
| Tighten feeder cutoff ($d_{\text{feeder\_cutoff}}$) | Fewer stations qualify as catchment candidates | Locality queries return fewer candidate deboarding stations |

All parameters are defined in code with documented defaults. Sensitivity testing can be performed by varying parameters per-query through the API or by modifying defaults in the engine services and re-running the 63-test suite.
